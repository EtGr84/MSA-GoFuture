# РАЗДЕЛ 2. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
---
| № | Требование |
| :-: | :- |
| 1 | Realtime-признаки для pricing/fraud должны обновляться с задержкой до минут. |
| 2 | BI-витрины должны иметь понятные SLA freshness и completeness. |
| 3 | Пайплайн должен поддерживать replay событий и backfill исторических данных. |
| 4 | PII должна маскироваться или токенизироваться до глобальных аналитических слоёв. |
| 5 | Каждая витрина и feature set должны иметь владельца, описание, lineage и data quality checks. |
| 6 | ML-модели должны версионироваться, проходить offline/online validation и иметь rollback. |

# РАЗДЕЛ 3. РЕШЕНИЕ
---

Выбираем layered data platform:

- Bronze: сырые события Kafka и CDC, записанные в object storage без потери исходного контракта.
- Silver: очищенные, нормализованные и дедуплицированные таблицы с data quality checks.
- Gold: бизнес-витрины, агрегаты и feature sets для BI и ML.

Flink обрабатывает realtime-потоки для pricing signals, driver utilization, hot zones и fraud features. Spark используется для batch backfill, обучения моделей и тяжёлых исторических агрегаций. ClickHouse остаётся основным хранилищем BI-витрин, DataLens — BI-инструментом. Для ML добавляем Feature Store, Model Registry и Model Serving.


# Механизмы обеспечения качества данных

## Data contracts

Каждый producer публикует события по контракту:

- schema в Schema Registry;
- владелец домена и Slack/On-call канал;
- описание полей и PII-классификация;
- правила compatibility;
- SLA freshness и допустимый lag;
- список downstream consumers.

Несовместимые изменения блокируются contract tests в CI/CD producer-сервиса.

## Quality gates

| Слой | Проверки | Что происходит при ошибке |
| --- | --- | --- |
| Ingestion | schema validation, required fields, event_id uniqueness | Событие уходит в quarantine/DLQ. |
| Bronze | append-only запись, контроль количества, checksum, partition completeness | Остановка promotion в Silver. |
| Silver | дедупликация, referential checks, valid ranges, PII masking | Ошибка качества, алерт владельцу домена. |
| Gold | бизнес-инварианты, freshness, metric reconciliation | Витрина помечается stale, DataLens показывает предупреждение. |
| Feature Store | training/serving skew, null rate, drift, freshness | Модель не получает новый feature set или откатывается на предыдущий. |

## Проверки по доменам

| Домен | Примеры проверок |
| --- | --- |
| Booking | `TripCompleted` не может быть без `BookingCreated`; статус поездки меняется только по допустимому графу. |
| Driver | GPS-точки должны быть в допустимом регионе; скорость между точками не превышает физически возможный лимит. |
| Pricing | Цена не отрицательная; surge multiplier в допустимом диапазоне; quote TTL не истёк. |
| Payments | Суммы ledger сходятся; `PaymentCaptured` возможен только после `PaymentAuthorized`. |
| Fraud | Risk score находится в диапазоне 0..1; версия модели указана в каждом решении. |
| Analytics | Количество событий по источникам сверяется с Kafka offsets и ClickHouse inserts. |

## Lineage и каталог

Используем DataHub/OpenMetadata или аналогичный каталог:

- владельцы datasets и feature sets;
- связи `source topic -> bronze -> silver -> gold -> feature/model/dashboard`;
- PII tags;
- SLA и freshness;
- ссылки на проверки качества;
- история изменений схем.

## Наблюдаемость качества

Метрики:

- `data_freshness_seconds`;
- `data_completeness_ratio`;
- `schema_validation_failures_total`;
- `null_rate_by_field`;
- `duplicate_event_count`;
- `quarantine_events_total`;
- `feature_drift_score`;
- `training_serving_skew`;
- `model_prediction_latency_seconds`;
- `model_quality_metrics` по модели.

Алерты:

- freshness нарушен для gold-витрины;
- DLQ/quarantine > 0 для critical topic;
- резкий рост null/duplicate rate;
- drift выше порога;
- ClickHouse ingestion lag растёт дольше 15 минут;
- модель деградировала по online KPI.

## ML governance

- Каждый training dataset версионируется.
- Модель регистрируется в Model Registry с метриками, владельцем, датой и ссылкой на dataset lineage.
- Перед production-deploy выполняются offline validation, shadow/canary и business guardrails.
- Для dynamic pricing вводятся ограничения: max surge, explainability для бизнес-аудита, rollback.
- Для fraud detection сохраняются model version, feature snapshot и reason codes.

## Почему такой подход подходит

- Kafka и outbox из Task2 дают единый поток доменных событий.
- Flink закрывает near-real-time сценарии dynamic pricing и fraud.
- Spark удобен для исторических перерасчётов и обучения ML-моделей.
- ClickHouse уже есть в ландшафте компании и подходит для аналитических витрин.
- Feature Store снижает расхождение между training и serving.
- Data quality gates защищают BI и ML от тихих поломок данных.

## Альтернативы

| Альтернатива | Плюсы | Минусы |
| :- | :- | :- |
| Только ClickHouse без data lake | Быстрее старт для BI. | Сложнее replay/backfill, хранение сырых событий и ML training datasets. |
| Только batch-пайплайны | Проще эксплуатация. | Не подходит для realtime pricing, hot zones и fraud detection. |
| Отдельные витрины в каждом сервисе | Автономия команд. | Дублирование логики, разные определения метрик, сложно строить ML. |
| Полностью managed black-box ML-платформа | Меньше поддержки инфраструктуры. | Риск vendor lock-in и сложнее контролировать data residency. |

## Недостатки, ограничения, риски

- Data platform добавляет новые компоненты и эксплуатационную сложность.
- Без строгого ownership витрины быстро превратятся в набор конфликтующих метрик.
- Realtime features требуют контроля lag, backpressure и watermark.
- ML-модели могут деградировать из-за data drift и concept drift.
- PII в сырых событиях нужно блокировать контрактами и DLP, иначе растёт compliance-риск.

## Последствия

GoFuture получает общий data backbone для BI, ML и realtime-решений. Pricing, Fraud и Analytics перестают строить разрозненные пайплайны, а качество данных становится частью production-процесса: schema checks, validation, lineage, ownership и мониторинг.
