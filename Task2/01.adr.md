# РАЗДЕЛ 1. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

| Действующие лица или системы | Use Case | Описание |
| :- | :- | :- |
| Pricing Service | Динамическое ценообразование | Pricing получает потоковые сигналы спроса, предложения, ETA и зон для расчёта актуальной цены. |
| Notification Service | Асинхронные уведомления | По событиям поездки и платежей создаются команды на push-уведомления. |
| Kafka Event Backbone | Приём и доставка событий | Kafka принимает события, хранит их по топикам и доставляет независимым потребителям с партиционированием по регионам. |
| Analytics Service | BI и ML-потоки | События попадают в ClickHouse, витрины DataLens и feature pipelines для ML. |
| Доменные сервисы | Публикация событий | Booking, Driver, Pricing, Payments, Fraud и Geography публикуют доменные события после изменения своего состояния. |
| SRE и продуктовые команды | Мониторинг | Команды видят состояние Kafka, lag потребителей, ошибки схем, DLQ, Saga и бизнес-метрики. |
| Booking Service | Saga поездки | Booking координирует Saga создания поездки: цена, риск, назначение водителя, авторизация платежа, подтверждение. |
| Stream Processing | Потоковая обработка | Flink или Kafka Streams обрабатывают события водителей, поездок, платежей и спроса в realtime. |

# РАЗДЕЛ 2. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ


- Потребители должны быть идемпотентными и устойчивыми к дублям событий.
- Партиционирование должно учитывать `region_id`, чтобы масштабировать регионы независимо и упростить локальный комплаенс. 
- Мониторинг должен покрывать брокеры, producers, consumers, stream jobs, CDC, Saga и бизнес-SLO. 
- Публикация событий не должна теряться при сбое сервиса или брокера. 
- Событийная платформа должна поддерживать поток событий для 500 тысяч конкурентных поездок.
- Для poison messages должны быть retry topics и DLQ с понятной процедурой разбора. 
- Для событий одного агрегата должен сохраняться порядок обработки внутри партиции. 
- Контракты событий должны версионироваться и проверяться через Schema Registry. 
- События критичного пути должны обрабатываться локально в регионе, где выполняется поездка.

# РАЗДЕЛ 3. РЕШЕНИЕ

## 3.1 Выбираем Kafka как событийный backbone GoFuture.

- В каждом географическом регионе работает локальный Kafka-кластер, а межрегиональная репликация используется только для глобальной аналитики, комплаенс-разрешённых агрегатов и disaster recovery. Операционные события поездки остаются в регионе выполнения поездки.
- Сервисы публикуют события через transactional outbox: бизнес-транзакция записывает доменное состояние и outbox-запись в локальную БД, затем Debezium/Kafka Connect публикует событие в Kafka. Это убирает риск рассинхронизации между записью в БД и отправкой события.
- Формат событий фиксируется через envelope: `event_id`, `event_type`, `event_version`; `occurred_at`, `producer`, `schema_ref`;  `region_id`, `tenant_id`; `aggregate_type`, `aggregate_id`; `correlation_id`, `causation_id`, `idempotency_key`;`payload`.
- Топики проектируются по доменам: `gofuture.<domain>.<stream>.v<version>`. Партиционирование выполняется ключом `region_id + aggregate_id`. Для high-volume геособытий используется `region_id + geo_cell_id + driver_id`, чтобы распределить нагрузку и сохранить локальность обработки.

## 3.2 Realtime-обработка выполняется Flink или Kafka Streams:

- расчёт сигналов спроса и предложения для Pricing;
- агрегация доступности водителей и горячих зон для Geography;
- подготовка признаков для Fraud;
- потоковые витрины для Analytics и DataLens.
- Для бизнес-процесса создания поездки выбираем оркестрируемую Saga в Booking Service. Booking хранит состояние Saga, отправляет команды участникам и реагирует на события результата. Компенсации: освобождение назначенного водителя, отмена/void авторизации платежа, перевод заказа в отменённый статус и уведомление клиента.

## 3.3 Обоснование выбора Kafka

- Kafka хорошо подходит для high-throughput событий и независимых consumer groups.
- Партиции позволяют масштабировать обработку по регионам, городам и агрегатам.
- Retention даёт возможность переигрывать события для аналитики, ML и восстановления проекций.
- Kafka Streams/Flink естественно интегрируются с Kafka и подходят для realtime pricing/fraud/analytics.
- Экосистема Kafka Connect и Debezium упрощает transactional outbox и CDC.

# РАЗДЕЛ 4. МОДЕЛЬ СОБЫТИЙ, ТОПИКИ KAFKA, SAGA

## 4.1 Модель доменных событий

Событие описывает уже произошедший факт в домене. Названия формулируются в прошедшем времени: `BookingCreated`, `DriverLocationUpdated`, `PaymentAuthorized`.

Базовый envelope:

| Поле | Назначение |
| --- | --- |
| `event_id` | Уникальный UUID события для дедупликации. |
| `event_type` | Тип события, например `BookingCreated`. |
| `event_version` | Версия контракта события. |
| `occurred_at` | Время факта в домене. |
| `producer` | Сервис-владелец события. |
| `region_id` | Регион выполнения поездки или владения данными. |
| `tenant_id` | Партнёр/арендатор платформы для мультиарендности. |
| `aggregate_type` | Тип агрегата: `booking`, `driver`, `payment`. |
| `aggregate_id` | Идентификатор агрегата, по которому нужен порядок. |
| `correlation_id` | Сквозной идентификатор пользовательского сценария. |
| `causation_id` | Идентификатор команды или события-причины. |
| `idempotency_key` | Ключ для безопасного повторного выполнения. |
| `schema_ref` | Ссылка на схему в Schema Registry. |
| `payload` | Данные события без лишних PII. |

## 4.3 Kafka-топики и партиционирование

Формат имени: `gofuture.<domain>.<stream>.v<version>`.

События содержат `region_id`, а ключ партиционирования начинается с региона. Для большинства доменов ключ: `region_id + aggregate_id`. Для геопозиции водителя ключ: `region_id + geo_cell_id + driver_id`, чтобы распределять high-volume события по геоячейкам.

| Топик | Примеры событий | Partition key | Потребители |
| --- | --- | --- | --- |
| `gofuture.booking.events.v1` | `BookingCreated`, `BookingConfirmed`, `TripCompleted` | `region_id + booking_id` | Pricing, Driver, Payments, Fraud, Notification, Analytics |
| `gofuture.driver.availability.v1` | `DriverAvailabilityChanged`, `DriverShiftStarted` | `region_id + driver_id` | Booking, Geography, Analytics |
| `gofuture.driver.location.v1` | `DriverLocationUpdated` | `region_id + geo_cell_id + driver_id` | Geography, Pricing signals, Analytics |
| `gofuture.geography.events.v1` | `DriverCandidatesFound`, `RouteCalculated`, `HotZoneDetected` | `region_id + geo_cell_id` | Booking, Pricing, Analytics |
| `gofuture.pricing.events.v1` | `PriceQuoteRequested`, `PriceCalculated`, `SurgeMultiplierChanged` | `region_id + quote_id` | Booking, Analytics, Fraud |
| `gofuture.fraud.decisions.v1` | `FraudApproved`, `FraudRejected`, `RiskScoreChanged` | `region_id + booking_id/payment_id` | Booking, Payments, Analytics |
| `gofuture.payments.events.v1` | `PaymentAuthorized`, `PaymentFailed`, `PayoutCreated` | `region_id + payment_id` | Booking, Notification, Analytics, Fraud |
| `gofuture.notification.commands.v1` | `NotificationRequested` | `region_id + user_id` | Notification Service |
| `gofuture.analytics.raw.v1` | Нормализованные доменные события | `region_id + event_id` | Analytics Service, ML pipelines |
| `gofuture.<domain>.retry.v1` | Повторная обработка | исходный key | Исходный consumer group |
| `gofuture.<domain>.dlq.v1` | Poison messages | исходный key | Support tooling, SRE |

## 4.5 Saga поездки

Выбран тип Saga: оркестрируемая Saga. Оркестратор находится в Booking Service, потому что Booking владеет пользовательским процессом поездки и должен явно управлять статусами, таймаутами и компенсациями.

### Основной happy path:

1. `BookingCreated`.
2. Booking отправляет `PriceQuoteRequested`.
3. Pricing публикует `PriceCalculated`.
4. Booking отправляет `FraudCheckRequested`.
5. Fraud публикует `FraudApproved`.
6. Booking отправляет `DriverAssignmentRequested`.
7. Driver/Geography публикуют `DriverAssigned`.
8. Booking отправляет `PaymentAuthorizationRequested`.
9. Payments публикует `PaymentAuthorized`.
10. Booking публикует `BookingConfirmed`.
11. Notification получает `NotificationRequested`.

---

### 4.6 Компенсации:

| Ошибка | Компенсация |
| --- | --- |
| Цена не рассчитана или истёк TTL котировки | `BookingCancelled`, уведомление пользователя. |
| Fraud отклонил поездку | `BookingCancelled`, водитель не назначается, событие уходит в Analytics. |
| Водитель не найден | `BookingCancelled` или перевод в ожидание, если продуктово допустимо. |
| Платёж не авторизован | `DriverAssignmentReleased`, `BookingCancelled`, уведомление пользователя. |
| Timeout участника Saga | Повтор команды, затем компенсация и DLQ для ручного разбора. |

Состояние Saga хранится в Booking DB. Все команды имеют `idempotency_key`, а участники сохраняют обработанные `event_id`/`command_id` в inbox-таблицах.

# РАЗДЕЛ 5. АЛЬТЕРНАТИВЫ 

| Альтернатива | Плюсы | Минусы |
| :- | :- | :- |
| RabbitMQ как единственный broker | Уже используется в текущем стеке, проще для командных очередей. | Слабее подходит для replay, долгого retention, больших потоков и независимых аналитических потребителей. |
| Только синхронный REST между сервисами | Проще трассировать отдельный запрос. | Усиливает связность, повышает риск каскадных отказов и не решает realtime-аналитику. |
| Полностью choreography Saga | Меньше центральной логики. | Сложнее понять состояние поездки, компенсации и таймауты в критичном пользовательском сценарии. |
| Единый глобальный Kafka-кластер | Проще администрирование топиков. | Хуже latency, выше межрегиональные риски, сложнее локальный комплаенс и изоляция сбоев. |

# РАЗДЕЛ 6. НЕДОСТАТКИ, РИСКИ

- Eventual consistency усложняет диагностику пользовательских сценариев.
- Kafka требует дисциплины по схемам, retention, партициям и consumer lag.
- Неправильно выбранный partition key может создать горячие партиции, особенно для геособытий в мегаполисах.
- Outbox/CDC добавляет задержку между записью в БД и публикацией события.
- Оркестрируемая Saga делает Booking Service владельцем процесса и требует аккуратного управления таймаутами.
- Exactly-once гарантии ограничены границами Kafka Streams/Flink; на внешних side effects всё равно нужна идемпотентность.

# РАЗДЕЛ 7. МОНИТРИНГ

## 7.1 Уровни мониторинга

Мониторинг строится вокруг трёх уровней:

1. Бизнес-SLO: поездка создана, водитель назначен, цена рассчитана, платёж авторизован, уведомление доставлено.
2. Event platform health: Kafka, Schema Registry, Connect/Debezium, retry/DLQ, consumer lag.
3. Processing health: producers, consumers, Flink/Kafka Streams jobs, Saga и внешние интеграции.

Для всех событий и команд используется единый `correlation_id`, чтобы связать метрики, логи и трейсы в одном пользовательском сценарии.

## 7.4 Реакция на инциденты

- При росте consumer lag: проверить broker health, consumer errors, recent deploys, размер партиций, backpressure stream jobs.
- При DLQ: остановить авто-retry для poison message, сохранить payload, проверить schema/version, завести remediation task.
- При ошибках Schema Registry: заблокировать rollout producer, откатить несовместимую схему, запустить contract tests.
- При сбое Saga: включить компенсации, проверить stuck states, сверить Booking/Payments/Driver.
- При межрегиональной деградации: остановить репликацию некритичных аналитических потоков и сохранить локальную обработку поездок.
