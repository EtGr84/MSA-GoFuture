# ADR: глобальное развёртывание и отказоустойчивость GoFuture

---

# РАЗДЕЛ 1. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ 

| Действующие лица или системы | Use Case | Описание |
| :- | :- | :- |
| Global Traffic Manager | Failover | При деградации региона трафик переводится на ближайший здоровый регион. |
| Доменные сервисы | Локальная обработка поездки | Booking, Driver, Pricing, Payments, Geography и Fraud обрабатывают поездку в регионе её выполнения. |
| Compliance | Локальное хранение данных | PII и платежные данные остаются в разрешённых юрисдикциях. |
| Пассажиры и водители | Низкая задержка | Пользователь направляется в ближайший здоровый регион через GeoDNS/Anycast. |
| SRE | Управление инцидентами | SRE видит health checks, SLO, lag репликации, ошибки WAF и выполняет controlled failover. |
| Data Platform | Межрегиональная репликация | Операционные данные реплицируются только по разрешённым потокам, аналитические агрегаты уходят в глобальный слой. |
| Regional API Edge | Приём трафика | Каждый регион принимает мобильный и web-трафик через WAF, DDoS protection, firewall и API Gateway. |

# РАЗДЕЛ 2. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

- Межсервисный трафик должен быть защищён mTLS и network policies.
- Региональный сбой не должен приводить к глобальной недоступности платформы.
- Платформа должна работать более чем в трёх географических регионах.
- Межрегиональная репликация должна учитывать локальный комплаенс и минимизацию PII.
- Доступность критичного пути заказа поездки должна быть 99,99%.
- Все внешние входы должны проходить через WAF, DDoS protection, firewall и rate limiting.
- Активные поездки должны продолжать обслуживаться локально, а при failover получать контролируемую деградацию.
- Пользовательский трафик должен направляться в ближайший здоровый регион.

# Раздел 3. РЕШЕНИЕ

---

3.1 Выбираем active-active развёртывание в четырёх пользовательских runtime-регионах:

- SEA-1 Singapore;
- SEA-2 Jakarta;
- LATAM-1 Sao Paulo;
- LATAM-2 Santiago.

---

3.2 Control/partner region Kazakhstan/Russia остаётся отдельным управляющим и back-office контуром для текущего Yandex Cloud landscape, но не засчитывается как пользовательский регион высокой доступности.

---

3.3 Для Юго-Восточной Азии пара Singapore + Jakarta закрывает крупные рынки региона, снижает latency и даёт региональный failover внутри SEA. Для Южной Америки пара Sao Paulo + Santiago даёт второй конкретный runtime-контур: Sao Paulo обслуживает Brazil/eastern South America, Santiago обслуживает Chile/Andean corridor и принимает LATAM failover при деградации Sao Paulo. При обратной деградации Santiago трафик переводится в Sao Paulo.

---

3.4 Так как официальная документация Yandex Cloud указывает регионы Russia и Kazakhstan, для SEA и LATAM используется cloud-agnostic regional runtime. Singapore, Jakarta и Sao Paulo могут быть размещены в AWS или эквивалентном провайдере, а Santiago — в Google Cloud `southamerica-west1` или эквивалентном локальном провайдере. Платформа остаётся переносимой: Kubernetes, Kafka, PostgreSQL, ClickHouse, Terraform, GitOps, единые security policies.

---

3.5 Выбранные подходы и технологии

- Read-local/write-local для операционных данных поездки.
- Региональные пары failover: Singapore <-> Jakarta и Sao Paulo <-> Santiago.
- Service mesh mTLS и network policies внутри регионов.
- Edge WAF/DDoS protection, regional firewall, API rate limiting, bot protection.
- Глобальные аналитические агрегаты без PII.
- Failover через controlled traffic shift: 10% -> 50% -> 100%, если health checks и error budget позволяют.
- Regional Kafka clusters и PostgreSQL per service.
- GeoDNS/Anycast Global Traffic Manager с health checks на региональные API Gateway.
- Межрегиональная репликация событий через MirrorMaker 2 / Cluster Linking только для разрешённых топиков.
- Active-active региональные кластеры Kubernetes с независимыми доменными сервисами.

# Раздел 4. СТРАТЕГИЯ КОМПЛАЕНСА

---

4.1 Основные принципы

- Purpose limitation: каждый поток данных имеет владельца, назначение и срок хранения.
- Auditability: доступы, админские действия и межрегиональные экспорты логируются.
- Data minimization: события Kafka и аналитические витрины не содержат лишних PII.
- Encryption everywhere: TLS/mTLS in transit, KMS-managed encryption at rest.
- Data residency: PII, платежные данные и документы водителей хранятся в регионе или стране, где это требуется законом.

---

4.2 Классификация данных

| Класс данных | Примеры | Правило обработки |
| --- | --- | --- |
| Операционные события | BookingCreated, DriverAssigned | Реплицировать без лишних PII, использовать tenant/region labels. |
| Геоданные | GPS, маршруты, ETA | Хранить с ограниченным retention, агрегировать для аналитики. |
| Агрегаты | спрос по зонам, fraud features, BI metrics | Можно глобально использовать после обезличивания. |
| PII | Имя, телефон, email, документы водителя | Хранить локально, реплицировать только при законном основании. |
| Финансовые данные | Платежи, выплаты, ledger | Хранить в Payments region, использовать токенизацию, сверку и audit trail. |

---

4.3 Контрольные меры

- DPIA/PIA перед запуском нового региона.
- Pseudonymization/tokenization для user_id, driver_id, payment_id в глобальных потоках.
- Локальные payment/fiscal требования обрабатываются в Payments Service конкретного региона.
- IAM least privilege и регулярный access review.
- Legal hold и right-to-erasure process с учётом локальных законов.
- Региональные KMS-ключи, раздельные по региону и tenant.
- Data retention policies: отдельные сроки для поездок, геотреков, логов, платежей.
- DLP checks для Kafka topics и data lake ingestion.

4.4 Межрегиональные потоки

---

Разрешены:

- агрегаты спроса и предложения без PII;
- fraud intelligence без персональных полей;
- технические метрики и обезличенные логи;
- справочники тарифов и зон, если они не содержат персональных данных.

Запрещены по умолчанию:

- документы водителей;
- полные профили пассажиров;
- полные GPS-треки с user/driver identity;
- платежные реквизиты и банковские данные.

# РАЗДЕЛ 5. СЦЕНАРИИ ОТКАЗА

---

5.1 Сценарии отказа

| Сценарий | Детекция | Автоматическое действие | Ручное действие SRE | RTO/RPO |
| --- | --- | --- | --- | --- |
| Отказ платёжного провайдера | Payment error rate, synthetic checks | Circuit breaker, fallback provider при наличии, retry | Переключить routing платежей, уведомить бизнес | RTO 5-15 минут, RPO 0 для ledger |
| Недоступен LATAM-2 Santiago | Global health checks, synthetic probes, Kafka lag | Трафик Chile/Andean corridor переводится в LATAM-1 Sao Paulo | Контроль latency, capacity и локальных compliance-ограничений | RTO до 15 минут, RPO до 1 минуты |
| Падение одного pod/instance сервиса | Kubernetes health checks, Prometheus alert | Перезапуск pod, пересоздание instance, исключение из service discovery | Проверить error budget и recent deploy | RTO до 2 минут, RPO 0 для committed данных |
| Ошибка WAF/rule rollout | Рост false positives, падение successful requests | Rollback rule set | Разобрать sample blocked requests | RTO до 10 минут |
| Недоступен регион SEA-1 Singapore | Global health checks, synthetic probes, Kafka lag | GeoDNS/Anycast переводит трафик SEA в SEA-2 Jakarta | Controlled failover 10/50/100%, включить degraded mode для активных поездок | RTO до 15 минут, RPO до 1 минуты по событиям |
| Компрометация региона или data breach | Security alerts, SIEM, anomalous access | Изоляция региона firewall/security groups | Incident response, rotation secrets, legal/compliance process | По playbook |
| Рост replication lag | MirrorMaker/Cluster Linking lag | Замедлить некритичные аналитические потоки | Проверить сеть, quotas, hot partitions | RTO не применимо, RPO зависит от lag |
| Деградация одной AZ | Load balancer health checks, рост 5xx/latency | Трафик уходит в здоровые AZ региона | Заморозить deploy, проверить capacity | RTO до 5 минут, RPO 0-минуты |
| Недоступен LATAM-1 Sao Paulo | Global health checks, synthetic probes, Kafka lag | Новые LATAM-запросы переводятся в LATAM-2 Santiago | Controlled failover 10/50/100%, приоритизировать активные поездки и платежи | RTO до 15 минут, RPO до 1 минуты по разрешённым событиям |
| Сбой Kafka в регионе | Broker metrics, under replicated/offline partitions | Producers переходят в локальный outbox buffer, consumers останавливают offsets | Восстановить broker/partition, затем replay outbox | RTO до 30 минут, RPO 0 при сохранной БД |
| Недоступен регион SEA-2 Jakarta | Global health checks | Трафик Indonesia временно переводится в Singapore | Контроль latency и capacity SEA-1 | RTO до 15 минут, RPO до 1 минуты |

---

5.2 Правила failover

- При нехватке capacity отключаются некритичные сценарии: промо, часть аналитики, тяжелые отчёты, неважные уведомления.
- Активные поездки по возможности завершаются в исходном регионе; новые поездки отправляются в failover-регион.
- После восстановления выполняется failback только вручную и только после сверк
- Автоматически переключаются только health-check очевидные сценарии: недоступность endpoint, массовые 5xx, offline region.
- Переключение региона выполняется controlled traffic shift: 10% -> 50% -> 100%.

# РАЗДЕЛ 6. ВЫБОР РЕГИОНОВ РАЗВЕРТЫВАНЯ

---

6.1 Выбранные регионы

| Регион | Назначение | Почему выбран |
| --- | --- | --- |
| SEA-1 Singapore | Основной регион Юго-Восточной Азии | Хорошая сетевая связность региона, зрелая облачная инфраструктура, удобен как первый SEA hub. |
| SEA-2 Jakarta | Второй активный регион Юго-Восточной Азии | Близость к крупному рынку Индонезии, снижает latency и даёт failover внутри SEA. |
| LATAM-1 Sao Paulo | Основной регион для Brazil/eastern South America | Ближайший крупный облачный регион для Бразилии, Аргентины, Уругвая и части соседних стран. |
| LATAM-2 Santiago | Второй активный регион Южной Америки | Закрывает Chile/Andean corridor и даёт конкретный failover-контур для LATAM вместо неопределённого warm standby. |

Отдельно сохраняется Control/Partner Kazakhstan/Russia для back-office, текущих клиентов, CI/CD, GitOps, глобального управления и корпоративных сценариев. Этот контур не считается пользовательским runtime-регионом для SLA 99,99%.

---

6.2 Логика выбора

GoFuture расширяется в Юго-Восточную Азию и Южную Америку, поэтому пользовательские операции поездки должны выполняться рядом с пользователем и водителем. Для поездки выбирается регион по `trip_region_id`, а не по случайному текущему IP, чтобы водитель, пассажир, цена, география и платёжный контур оставались в одной региональной зоне обработки.

На первом этапе используем 4 пользовательских runtime-региона. Это выполняет требование «более чем в трёх географических регионах» без искусственного зачёта control-plane. Для каждого целевого макрорегиона есть пара failover: Singapore <-> Jakarta для SEA и Sao Paulo <-> Santiago для LATAM.

---

6.3 Cloud placement

Текущий стек описывает Yandex Cloud, но для SEA и LATAM нужно использовать cloud-agnostic runtime или multi-cloud. Причина практичная: Yandex Cloud официально указывает регионы Russia и Kazakhstan, а целевые рынки требуют локального размещения ближе к пользователю.

Практичный placement:

- Singapore, Jakarta, Sao Paulo: AWS или эквивалентный провайдер с нужными managed Kubernetes/Kafka/PostgreSQL возможностями.
- Santiago: Google Cloud `southamerica-west1` или эквивалентный провайдер с регионом в Chile.
- Kazakhstan/Russia: control-plane и текущий Yandex Cloud контур без пользовательского failover-трафика новых SEA/LATAM рынков.

Все региональные кластеры проектируются переносимыми: Kubernetes, Kafka, PostgreSQL, ClickHouse, Terraform/GitOps, единые observability и security policies.

---

6.4 Latency и доступность

| Пользователь | Основной регион | Failover |
| --- | --- | --- |
| Singapore, Malaysia, Thailand, Vietnam, Philippines | SEA-1 Singapore | SEA-2 Jakarta |
| Indonesia | SEA-2 Jakarta | SEA-1 Singapore |
| Brazil, Argentina, Uruguay, Paraguay | LATAM-1 Sao Paulo | LATAM-2 Santiago |
| Chile, Peru, Colombia, Andean corridor | LATAM-2 Santiago | LATAM-1 Sao Paulo |
| Текущие клиенты и back-office | Kazakhstan/Russia control region | ручной DR по отдельному back-office playbook |

---

6.5 Ограничения

- Multi-cloud повышает сложность сети, IAM federation, IaC и эксплуатации, но убирает зависимость от отсутствия нужных регионов у одного провайдера.
- Платёжные интеграции и data residency могут требовать отдельной локальной обработки по стране.
- Глобальные fraud/analytics модели получают агрегаты и признаки без лишних PII.

# РАЗДЕЛ 7. АЛЬТЕРНАТИВЫ

| Альтернатива | Плюсы | Минусы |
| :- | :- | :- |
| Один глобальный регион | Проще эксплуатация. | Не выполняет низкую задержку и 99,99% при региональном сбое. |
| Active-passive по континентам | Дешевле active-active. | Хуже RTO, холодные кэши, больше риск при резком failover. |
| Единая глобальная БД с синхронной записью | Сильная консистентность. | Высокая latency, риск глобальных блокировок, сложно соблюдать data residency. |
| Полностью независимые региональные платформы без репликации | Максимальная изоляция. | Нет глобальной аналитики, сложнее партнёрские сценарии и fraud intelligence. |

# РАЗДЕЛ 8. ОГРАНИЧЕНИЯ И РИСКИ

- Active-active дороже и сложнее single-region развёртывания.
- Межрегиональная согласованность будет eventual consistency.
- При failover активные поездки могут временно перейти в degraded mode: без новой цены, без назначения нового водителя или с delayed notifications.
- Нужно жёстко контролировать PII в событиях, иначе репликация нарушит локальный комплаенс.
- Cloud-agnostic подход требует зрелого IaC, GitOps и платформенных стандартов.
- Multi-cloud для LATAM-2 добавляет требования к сетевой связности, IAM federation и единой модели observability/security.
