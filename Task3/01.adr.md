# РАЗДЕЛ 1. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ 

| Действующие лица или системы | Use Case | Описание |
| :- | :- | :- |
| Global Traffic Manager | Failover | При деградации региона трафик переводится на ближайший здоровый регион. |
| Доменные сервисы | Локальная обработка поездки | Booking, Driver, Pricing, Payments, Geography и Fraud обрабатывают поездку в регионе её выполнения. |

| Data Platform | Межрегиональная репликация | Операционные данные реплицируются только по разрешённым потокам, аналитические агрегаты уходят в глобальный слой. |
| Regional API Edge | Приём трафика | Каждый регион принимает мобильный и web-трафик через WAF, DDoS protection, firewall и API Gateway. |

№ ЕЛ 2. НЕФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ











## Нефункциональные требования

| № | Требование |
| :-: | :- |
| 1 | Доступность критичного пути заказа поездки должна быть 99,99%. |
| 2 | Платформа должна работать более чем в трёх географических регионах. |
| 3 | Пользовательский трафик должен направляться в ближайший здоровый регион. |
| 4 | Региональный сбой не должен приводить к глобальной недоступности платформы. |
| 5 | Активные поездки должны продолжать обслуживаться локально, а при failover получать контролируемую деградацию. |
| 6 | Межрегиональная репликация должна учитывать локальный комплаенс и минимизацию PII. |
| 7 | Все внешние входы должны проходить через WAF, DDoS protection, firewall и rate limiting. |
| 8 | Межсервисный трафик должен быть защищён mTLS и network policies. |

## Решение

Выбираем active-active развёртывание в четырёх пользовательских runtime-регионах:

- SEA-1 Singapore;
- SEA-2 Jakarta;
- LATAM-1 Sao Paulo;
- LATAM-2 Santiago.

Control/partner region Kazakhstan/Russia остаётся отдельным управляющим и back-office контуром для текущего Yandex Cloud landscape, но не засчитывается как пользовательский регион высокой доступности.

Для Юго-Восточной Азии пара Singapore + Jakarta закрывает крупные рынки региона, снижает latency и даёт региональный failover внутри SEA. Для Южной Америки пара Sao Paulo + Santiago даёт второй конкретный runtime-контур: Sao Paulo обслуживает Brazil/eastern South America, Santiago обслуживает Chile/Andean corridor и принимает LATAM failover при деградации Sao Paulo. При обратной деградации Santiago трафик переводится в Sao Paulo.

Так как официальная документация Yandex Cloud сейчас указывает регионы Russia и Kazakhstan, для SEA и LATAM используется cloud-agnostic regional runtime. Singapore, Jakarta и Sao Paulo могут быть размещены в AWS или эквивалентном провайдере, а Santiago — в Google Cloud `southamerica-west1` или эквивалентном локальном провайдере. Платформа остаётся переносимой: Kubernetes, Kafka, PostgreSQL, ClickHouse, Terraform, GitOps, единые security policies.

## Механизмы

- GeoDNS/Anycast Global Traffic Manager с health checks на региональные API Gateway.
- Edge WAF/DDoS protection, regional firewall, API rate limiting, bot protection.
- Active-active региональные кластеры Kubernetes с независимыми доменными сервисами.
- Региональные пары failover: Singapore <-> Jakarta и Sao Paulo <-> Santiago.
- Regional Kafka clusters и PostgreSQL per service.
- Межрегиональная репликация событий через MirrorMaker 2 / Cluster Linking только для разрешённых топиков.
- Read-local/write-local для операционных данных поездки.
- Глобальные аналитические агрегаты без PII.
- Service mesh mTLS и network policies внутри регионов.
- Failover через controlled traffic shift: 10% -> 50% -> 100%, если health checks и error budget позволяют.

## Альтернативы

| Альтернатива | Плюсы | Минусы |
| :- | :- | :- |
| Один глобальный регион | Проще эксплуатация. | Не выполняет низкую задержку и 99,99% при региональном сбое. |
| Active-passive по континентам | Дешевле active-active. | Хуже RTO, холодные кэши, больше риск при резком failover. |
| Единая глобальная БД с синхронной записью | Сильная консистентность. | Высокая latency, риск глобальных блокировок, сложно соблюдать data residency. |
| Полностью независимые региональные платформы без репликации | Максимальная изоляция. | Нет глобальной аналитики, сложнее партнёрские сценарии и fraud intelligence. |

## Недостатки, ограничения, риски

- Active-active дороже и сложнее single-region развёртывания.
- Межрегиональная согласованность будет eventual consistency.
- При failover активные поездки могут временно перейти в degraded mode: без новой цены, без назначения нового водителя или с delayed notifications.
- Нужно жёстко контролировать PII в событиях, иначе репликация нарушит локальный комплаенс.
- Cloud-agnostic подход требует зрелого IaC, GitOps и платформенных стандартов.
- Multi-cloud для LATAM-2 добавляет требования к сетевой связности, IAM federation и единой модели observability/security.

## Последствия

GoFuture получает архитектуру для низкой задержки в целевых регионах и отказоустойчивости уровня 99,99%. Региональные сбои изолируются, пользовательский трафик переводится в ближайший здоровый регион, а данные реплицируются по контролируемым потокам с учётом комплаенса.
