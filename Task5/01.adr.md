# ADR: Мультитенантная платформа
---

# РАЗДЕЛ 1. ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

| Действующие лица или системы | Use Case | Описание |
| :- | :- | :- |
| Domain Services | Tenant-aware обработка | Каждый запрос содержит `tenant_id`, `region_id`, `partner_id` и проверяется policy enforcement. |
| Partner Admin | Управление пользователями | Администратор партнёра подключает SSO, назначает роли и управляет доступами. |
| Data Platform | Изоляция данных | PII, платежные и операционные данные не смешиваются между партнёрами. |
| Tenant Management | Provisioning tenant | Создаются tenant record, ключи шифрования, схемы/БД, quotas, feature flags и monitoring labels. |
| Партнёр | Подключение к платформе | Партнёр подаёт заявку, выбирает регион, настройки, интеграции и модель изоляции. |
| Observability | Мониторинг tenant | SLO, ошибки, потребление ресурсов, cost и security events доступны в разрезе tenant. |
| IAM/IdP | Аутентификация и авторизация | Платформа поддерживает OIDC/SAML SSO, MFA, RBAC/ABAC и service accounts. |

# РАЗДЕЛ 2. НЕФУКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ

- Данные партнёров должны быть изолированы на уровне доступа, хранения и ключей шифрования.
- Подключение стандартного партнёра должно занимать часы/дни, а не недели ручной работы.
- IAM должен поддерживать SSO, MFA, audit logs и least privilege.
- Авторизация должна быть tenant-scoped и region-scoped.
- Платформа должна поддерживать разные уровни изоляции: pooled, bridge и silo.
- Метрики, логи и billing/cost должны иметь tenant labels.
- Ошибка или перегрузка одного tenant не должна влиять на остальных.

# РАЗДЕЛ 3. ПРЕДЛАГАЕМОЕ РЕШЕНИЕ
---

## 3.1 Выбираем модель control plane + tenant-aware data plane.

---

### 3.1.1 Control plane:

- IAM/IdP;
- Policy Engine;
- GitOps/IaC provisioning;
- Tenant Observability.
- Partner Portal;
- Onboarding Workflow;
- Tenant Registry;

---

### 3.1.2 Data plane:

- данные хранятся в tenant-scoped schemas/DBs;
- для крупных или регулируемых партнёров используется dedicated namespace/database;
- tenant keys в KMS разделяют криптографическую область;
- доменные сервисы получают tenant context из токена и API Gateway;
- Policy Enforcement проверяет RBAC + ABAC до выполнения действия;
- все события Kafka содержат `tenant_id` и `region_id`.

---

## 3.2 Роли и уровни доступа к данным

### 3.2.1 Модель доступа

---

Используется RBAC + ABAC:

- RBAC определяет допустимые действия роли.
- ABAC ограничивает область по `tenant_id`, `region_id`, `partner_id`, `data_class`, `purpose`.
- Все пользовательские токены и service tokens содержат tenant claims.
- Доступ к PII, платежам и документам требует MFA и audit trail.

---

### 3.2.2 Таблица ролей

| Роль | Кто использует | Доступ к данным | Уровень доступа | Ограничения |
| --- | --- | --- | --- | --- |
| Partner Finance | Финансы партнёра | Счета, выплаты, финансовые отчёты | Finance read/write | Только свой tenant и разрешённые регионы, MFA обязательно. |
| ML Engineer | Data/ML команда | Feature sets, model metrics, обезличенные training datasets | ML read/write | Нет доступа к raw PII; production deploy через approval. |
| SRE | GoFuture SRE | Метрики, логи, traces, health, quotas | Operate | PII в логах маскируется, доступ tenant-scoped при инциденте. |
| Data Analyst | Аналитик партнёра | BI-витрины и агрегаты | Analytics read | Только обезличенные данные своего tenant. |
| Service Account | Интеграции и сервисы | API по назначению | Machine-to-machine | Short-lived tokens, scoped permissions, rotation. |
| Partner Admin | Администратор партнёра | Пользователи, роли, настройки партнёра | Tenant admin | Только свой `tenant_id`, без доступа к GoFuture platform settings. |
| Driver Manager | Операции водителей | Профили водителей, документы, смены | Driver ops | Только свой регион/tenant, документы по least privilege. |
| Security Officer | GoFuture security | Audit logs, IAM events, policy decisions | Security admin | Не управляет бизнес-данными и платежами. |
| Support Agent | Поддержка | Заказы и обращения пользователей | Limited support | PII маскируется, действия записываются в audit log. |
| Platform Owner | GoFuture platform team | Все tenant metadata, platform config, агрегированные метрики | Admin | Нет прямого доступа к PII без break-glass процедуры. |
| Fraud Analyst | Антифрод | Risk decisions, fraud cases | Fraud read/write | Доступ к PII только по case и с audit trail. |
| Partner Developer | Техническая команда партнёра | API keys, webhooks, sandbox, технические логи | Developer | Только sandbox/prod своего tenant, без PII payload по умолчанию. |
| Read-only Auditor | Аудитор | Audit logs, настройки, финансовые отчёты | Read-only | Экспорт ограничен, PII маскируется. |
| Partner Operations Manager | Операции партнёра | Заказы, водители, зоны, SLA | Operational read/write | Нет доступа к полным платежным реквизитам. |

---

## 3.2.3 Уровни изоляции tenant

---

| Уровень | Для кого | Изоляция |
| --- | --- | --- |
| Pooled | Малые партнёры, sandbox | Shared compute, shared DB с RLS и tenant_id, tenant KMS key. |
| Bridge | Стандартный production | Shared compute, отдельная schema/database per tenant, tenant KMS key. |
| Silo | Крупные/регулируемые партнёры | Dedicated namespace, dedicated DB, отдельные quotas, выделенный observability slice. |

---

## Break-glass доступ

Break-glass разрешён только для инцидентов:

- approval от Security Officer или Incident Commander;
- ограничение по времени;
- обязательный MFA;
- запись всех действий в audit log;
- post-incident review.

## Почему такой подход подходит

- Control plane ускоряет onboarding и снижает ручную работу платформенной команды.
- RBAC + ABAC удобнее чистого RBAC: роль задаёт полномочия, а атрибуты ограничивают tenant, region и class данных.
- Tenant Registry становится единым источником правды для feature flags, quotas, compliance и routing.
- Модель pooled/bridge/silo позволяет балансировать стоимость и изоляцию.
- Tenant labels в observability помогают видеть noisy neighbor, ошибки интеграций и стоимость партнёра.

## Альтернативы

| Альтернатива | Плюсы | Минусы |
| :- | :- | :- |
| Отдельная инсталляция на каждого партнёра | Максимальная изоляция. | Дорого, медленный onboarding, сложно поддерживать единые релизы. |
| Только shared DB с `tenant_id` | Дешевле и проще старт. | Недостаточно для полной изоляции, выше риск утечки и noisy neighbor. |
| Только RBAC без ABAC | Проще модель ролей. | Сложно ограничить доступ по tenant, региону и классу данных. |
| Ручной onboarding через DevOps tickets | Не требует новой платформы. | Не выполняет цель быстрого запуска партнёров в новых регионах. |

## Недостатки, ограничения, риски

- Мультитенантность усложняет тестирование: нужен tenant isolation test suite.
- Dedicated tenant tier дороже и требует capacity planning.
- Ошибки в policy engine могут стать критичным security-инцидентом.
- Нужно строго следить, чтобы `tenant_id` не терялся в событиях, логах и асинхронных задачах.
- DataLens/BI и ML-витрины должны фильтроваться по tenant, иначе возможна утечка агрегатов.

## Последствия

GoFuture сможет подключать партнёров быстрее, сохраняя контроль доступа, изоляцию данных и наблюдаемость. Партнёры получают SSO и self-service управление пользователями, а платформа — автоматизированное provision окружения, tenant-aware мониторинг и управляемую модель изоляции.
